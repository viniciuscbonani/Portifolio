Investigação
industrial · Tractian

Um sistema com cinco agentes que investiga chamados de clientes da Tractian e sugere o próximo passo, com evals para medir cada mudança. A decisão final fica com uma pessoa.

Problema

Cada chamado precisa de um especialista.

A Tractian monitora máquinas industriais com sensores e modelos de IA que emitem diagnósticos automáticos. Quando o diagnóstico não bate com a expectativa do cliente, ele abre um chamado:

  • "O redutor quebrou ontem e eu não recebi nenhum aviso. Por quê?"
  • "O RMS está subindo há dias e nenhum insight foi gerado."
  • "Recebi um alerta de desbalanceamento, mas a máquina foi balanceada semana passada."

Responder exige investigar o estado técnico do ativo: se a referência estava válida, se os dados chegaram completos, se o modelo cobria aquele tipo de falha. Hoje um engenheiro faz isso à mão, e esse trabalho não escala.

Arquitetura

Como funciona.

Os agentes cuidam das partes que envolvem linguagem. Entre um agente e outro, as regras mais importantes rodam em código. O sistema só tem acesso de leitura à API industrial.

  1. Classificador LLM pequeno

    Decide se o caso pede contexto, investigação ou recomendação. Pedido de ação nunca vira autorização para executar.

  2. Agente de fontes LLM pequeno

    Planeja quais consultas fazer e escolhe até dois documentos reais da base de conhecimento. IDs inventados são descartados.

  3. Investigador LLM forte

    Consolida as evidências num relatório técnico, com hipóteses, lacunas e a citação que sustenta cada afirmação.

  4. Gate de suficiência código

    Verifica se a evidência necessária existe antes de permitir qualquer conclusão ou recomendação.

  5. Juiz LLM forte

    Revisa o relatório e registra objeções estruturadas. Ele aponta problemas, mas não decide o próximo passo.

  6. Compilador de revisão código

    Confere cada objeção contra as regras: volta para a etapa responsável, gera uma versão conservadora ou escala para um humano.

  7. Redator LLM menor

    Só escreve depois da aprovação: relatório para a engenharia e prévia de resposta ao cliente.

Decisões-chave

Escolhas que fiz.

  • O sistema só sugere

    O desafio original incluía executar ações na plataforma. No recorte final, o sistema prepara a ação e a justificativa, mas a execução depende de aprovação humana.

  • A checagem de evidência é feita em código

    A checagem olha para coisas que dá para verificar, como campos presentes nas consultas e conflitos já resolvidos. A "confiança" que o próprio LLM declara fica de fora.

  • Um juiz revisa antes do texto final

    O relatório é contestado antes de virar texto para o cliente. Se o juiz levantar uma objeção que o código não consegue verificar, o relatório é descartado e substituído por uma versão conservadora.

  • Cada investigação tem versão

    Cada investigação tem uma chave e uma assinatura do pipeline. Mudou o modelo, o prompt ou o contexto, vira uma nova revisão. Nada é reaproveitado depois de vencer.

Avaliação

Como avaliei.

  • 111casos de avaliação, separados em desenvolvimento, validação e teste
  • 0mutações inseguras e chamadas proibidas nos 17 fluxos de regressão
  • 100%de respostas no formato válido no modo de contingência

Os números acima vêm do modo de contingência, que testa orquestração, contratos e segurança com os agentes substituídos por regras locais. Eles não medem a qualidade dos LLMs. O próximo passo é rodar o benchmark completo com os cinco modelos reais e comparar o sistema com o gate ligado e desligado.
